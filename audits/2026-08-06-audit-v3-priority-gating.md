# Audit v3 — Priority & Gating Logic

Scope: does every requirement actually get checked, and do substantive checks outrank
mechanical ones? Code-logic only. No content review, no rejection-history re-scan, no
external research (see `2026-08-06-audit.md` and `-v2.md` for those).

Short answer to Austin's question: **the Coursera cover-letter miss was not a one-off
rubric gap.** It was one instance of a structural pattern that appears in at least four
independent places in this pipeline. In every case the pattern is the same shape: a
mechanical check is cheap, deterministic, and wired into the acceptance decision, while
the substantive judgment is expensive, LLM-produced, and wired in **only as a boolean or
not at all**. The rubric fix in `hiring_manager.py` was necessary and correct, but the
gating around it means that fix can be silently bypassed on the most common code path.

---

## 1. Verdict on the stage-5 / HM-restale lead

**CONFIRMED.** The final shipped draft can differ from the draft the hiring manager
actually approved, and the report, the CLI summary, and the tracker all present the
stale verdict as if it applied to the shipped text.

### Trace

`main.py:55-57` — `hiring_gate.run()` returns `hm_gate_result`, whose `.hm_result` and
`.passed` describe the draft as it stood at that moment.

`main.py:66` — `final_draft = hm_gate_result.draft`. Correct so far.

`main.py:84-104` — the stage-5 repair block:

```python
if final_style_issues:                                    # main.py:84
    final_draft = draft_agent.revise(                     # main.py:86-89
        posting.title, posting.description, background_subset, best_practices,
        final_draft, final_style_issues, [],
    )
    length_result = length_fit.enforce_one_page(...)      # main.py:90-92
    final_draft = length_result.draft                     # main.py:93
    final_score_result = score_agent.score(...)           # main.py:94-97
    final_style_issues = style_lint.lint_draft(...) + structure_lint.lint_draft(...)
```

Score is recomputed. Lint is recomputed. Length is recomputed. **`hiring_manager.review()`
is not called anywhere after line 57.** `grep -n "hiring_manager.review" ` returns exactly
one hit in the whole repo: `hiring_gate.py:57`.

Then:

- `main.py:117` — `fully_accepted` consumes `hm_gate_result.passed`, computed pre-repair.
- `main.py:128` — `structurally_capped` consumes `hm_gate_result.stopped_reason`, likewise.
- `main.py:144` — `report.build_report(..., hm_gate_result, ...)` → `report.py:82,133,138`
  print "Hiring manager verdict: advance", the impression, and the concern list, all
  describing a document that no longer exists.
- `main.py:159` → `output.save(..., hm_gate_result.hm_result.verdict)` → `output.py:108`
  → `tracker.upsert(hiring_manager=...)`. The spreadsheet column records the stale verdict.

### Severity: high, and it lands squarely on the Coursera failure class

`revise()` is not scoped to the resume. It returns a full `Draft` — both `resume` and
`cover_letter` are regenerated by the model (`draft_agent.py:407-416`, `_extract_draft`).
The only constraint is prose: *"Revise the resume and cover letter to address ONLY the
items above... Preserve everything else from the current draft unchanged"*
(`draft_agent.py:398-403`). That is a prompt-level request, not a code-level guarantee —
exactly the category this project's own auditor persona says needs a deterministic
backstop rather than a restated instruction.

More pointedly: the lint issues that *trigger* this repair pass are disproportionately
cover-letter issues. Of the 14 checks in `structure_lint.lint_draft` and the 4 in
`style_lint.lint`, the ones that fire on the cover letter are the salutation check
(`structure_lint.py:324-329`), the closing check (`:331-336`), the word-count check
(`:340-357`), contrast tone (`:384`), and all four style checks (`style_lint.py:127`).
So the most common trigger for the repair pass is a cover-letter defect, the repair pass
regenerates the cover letter, and the regenerated cover letter is never seen by the only
component in the system that can judge whether its opening hook makes sense for the
company. A repair triggered by "cover letter is 412 words" can rewrite the opening hook
freely, and nothing downstream checks the result for context fit.

There is also an unfortunate inverse correlation: the cleaner the draft, the fresher its
HM approval; the more the pipeline had to fix, the less HM validation the shipped
document has. Validation coverage is weakest exactly where the risk is highest.

### Exact fix

In `main.py`, inside the `if final_style_issues:` block, after `final_draft` is settled
(after line 93) and before the acceptance computation at line 112, re-run the HM once
against the repaired document and let that verdict supersede:

```python
    # The repair pass regenerates BOTH documents (draft_agent.revise returns a
    # full Draft; its "change only these items" constraint is prose, not code).
    # The HM verdict from stage 4 describes the pre-repair text, so re-run it
    # against what is actually about to ship.
    status.substep("Re-reviewing repaired draft with the hiring manager...")
    post_repair_hm = hiring_manager.review(
        posting.title, posting.description, gate.company_name,
        final_draft.resume, final_draft.cover_letter,
    )
    hm_gate_result = replace(
        hm_gate_result,
        draft=final_draft,
        hm_result=post_repair_hm,
        passed=post_repair_hm.verdict == "advance",
        # a fresh reject is not the all-structural early stop; clear the label
        stopped_reason=hm_gate_result.stopped_reason if post_repair_hm.verdict == "advance" else "",
    )
```

(`from dataclasses import replace`, and `hiring_manager` added to the `main.py:4` import
line.) Cost is one extra Sonnet call, and only on runs that actually repaired.

Two design notes worth deciding explicitly:

- **Do not add a second repair loop.** If the post-repair HM now rejects, the correct
  outcome is `manual_review` with the fresh concerns — not another revise/review cycle.
  Letting this become a loop reintroduces the unbounded-iteration problem the caps exist
  to prevent.
- **Cleaner alternative**, if you'd rather not special-case `main.py`: move the entire
  stage-5 repair *inside* `hiring_gate.run()` as a final "post-lint-repair re-review"
  step, so there is exactly one place in the codebase that owns the invariant
  *"`HiringGateResult.hm_result` always describes `HiringGateResult.draft`."* Right now
  that invariant holds inside `hiring_gate.py` (see §4) and is broken only by `main.py`
  reaching in and mutating the draft afterwards. That is the real architectural defect —
  v2's §2.5 recommendation (add a stage-5 repair pass) was implemented correctly as
  written, but it was written without accounting for the HM verdict it invalidates.

## 2. Other confirmed priority/gating gaps

### 2.1 — HIGH — A 2-page resume can ship as `accepted` with the report claiming 1 page

**Files:** `main.py:49-52`, `main.py:116`, `hiring_gate.py:91-92`

`length_result` is computed once at stage 3 (`main.py:50-52`) against the
**pre-hiring-manager** draft. `hiring_gate.run()` then mutates the draft
(`hiring_gate.py:88-90`) and runs its own `enforce_one_page` at `hiring_gate.py:91-92` —
but it keeps only `.draft` and discards the `LengthFitResult`. `HiringGateResult`
(`hiring_gate.py:36-42`) carries no page information at all.

Back in `main.py`, `length_result` is only recomputed inside the `if final_style_issues:`
block (`main.py:90-92`). So on any run where the HM revised the draft **and** stage-5 lint
came back clean:

- `length_result.fits_one_page` at `main.py:116` is a stale True about a superseded draft
- `length_result.page_count` at `main.py:152` and `report.py:81` reports the stale count
- `output.py:107` writes the stale page count to the tracker

The only length signal that does run on the final text is
`_check_resume_length_precheck` (`structure_lint.py:360-372`), which is a word-count
heuristic explicitly marked `"low"` severity — and `main.py:110` filters low out of
`blocking_style_issues`. So the one deterministic ground-truth check in the system (an
actual Word render, `word_pagecount.py`) is skipped on the shipping path, and its
non-blocking heuristic stand-in cannot compensate.

**Fix:** hoist the length check out of the conditional. Move it to just before the
acceptance computation and run it unconditionally on `final_draft`:

```python
length_result = length_fit.enforce_one_page(
    posting.title, posting.description, background_subset, best_practices, final_draft
)
final_draft = length_result.draft
```

Since `enforce_one_page` returns immediately when the render is already one page
(`length_fit.py:42-46`), the cost on the common path is one `.docx` build, no API call.
If you take this, note it re-mutates `final_draft`, so it must sit **before** the
post-repair HM re-review from §1, not after.

### 2.2 — HIGH — Integrity flags found at stage 5 are never repaired, but em dashes are

**Files:** `main.py:84`, `main.py:88`, `main.py:114`

The stage-5 repair is gated on `if final_style_issues:` (`main.py:84`) — lint issues only.
`final_score_result.integrity_flags` is not part of that condition. And when the repair
*does* fire, `main.py:88` passes `final_style_issues, []` — the integrity_flags argument
to `revise()` is hardcoded empty, even though `revise()` has a dedicated
`integrity_flags` parameter with its own prompt section (`draft_agent.py:388-390, 397`)
and known flags are sitting right there in scope.

Concrete failure: the Sonnet final score (`main.py:94-97`) finds a fabricated claim —
the exact thing this entire project is built to prevent. Zero lint issues. Result: no
repair attempt, `fully_accepted` fails at `main.py:114`, status is `manual_review`,
Austin fixes it by hand. Meanwhile a single em dash gets an automatic Sonnet repair pass.
The system's #1 principle has *less* automated remediation at the final stage than a
typographic tell does.

**Fix:** two lines.

```python
if final_style_issues or final_score_result.integrity_flags:      # main.py:84
    ...
    final_draft = draft_agent.revise(
        ..., final_draft, final_style_issues, final_score_result.integrity_flags,
    )                                                              # main.py:86-89
```

### 2.3 — HIGH — The HM decides "structural vs fixable" without the information needed to decide it

**Files:** `hiring_manager.py:1-15`, `:92-99`, `:227-231`; `hiring_gate.py:64-82`;
`main.py:125-133`, `:164-172`

`hiring_manager.review()` is deliberately denied the background document
(`hiring_manager.py:6-10` — a good design choice for its primary job). But the
`(fixable)` / `(structural)` tag it is asked to append (`hiring_manager.py:92-99`) is
defined as *"a fact about the candidate's actual history that no rewrite changes."*
Determining that requires knowing what is in `background.md`. The HM is being asked to
make a call on information it was intentionally not given, and its answer is trusted
unilaterally:

- `hiring_gate.py:64` — `fixable_gaps` filters on that self-tag
- `hiring_gate.py:66-82` — if every concern is self-tagged structural, the loop
  **terminates on attempt 1**, no revision attempted, and sets `stopped_reason`
- `main.py:125-133` — `stopped_reason` is the sole trigger for
  `accepted_structurally_capped`
- `main.py:164-170` — which prints "This packet is as strong as these two documents can
  be made... the fix is real new material in background.md or a different target role,
  not another draft."

So a single mis-tag turns a fixable drafting defect into a confident, wrong, terminal
message telling Austin the problem is his career, not the draft. The default is
correctly safe when the tag is *missing* (`hiring_manager.py:227` defaults to fixable),
but there is no guard against a tag that is present and wrong.

This matters directly for the new rubric item: the instructions at
`hiring_manager.py:132-143` tell the HM to flag a context-fit failure as "high-severity,
fixable" — but that is a prompt-level instruction, and if the model tags it structural
instead, the concern doesn't just get downgraded, it terminates the loop.

**Fix — deterministic backstop, not a stronger prompt.** Some categories are, by
definition, properties of the documents rather than of the candidate's history. In
`HMResult.as_gap_dicts()` (`hiring_manager.py:226-231`), force those to fixable:

```python
# Categories that describe the DOCUMENTS, not the candidate's history. The HM
# has no access to background.md, so it cannot competently judge "structural"
# here — and a false structural tag terminates the gate on attempt 1.
DOCUMENT_ONLY_CATEGORIES = {"cover_letter", "first_impression", "specificity"}
...
if category.lower() in DOCUMENT_ONLY_CATEGORIES:
    fixable = True
```

A dental-practice hook sent to an education company cannot be a fact about Austin's work
history under any reading. Neither can "the top third doesn't signal the role" or "this
bullet is too vague to be checkable." `seniority_calibration`, `narrative_coherence`, and
`red_flag` legitimately can be structural and should keep honoring the model's tag.

Optional stronger version: gate the early stop on *two* attempts rather than one, so a
mis-tagged structural verdict on attempt 1 still gets one revision.

### 2.4 — MEDIUM — `jd_coverage` is a usable escape hatch, and the score prompt pays for using it

**Files:** `score_agent.py:38-56`, `:141-151`; `supervisor.py:47-52`; `report.py:51-55`,
`:111-114`; `background_loader.py:68-78`

Two independent problems, one of which is mechanical and fixable.

**(a) The classification is scored, and the incentive points one way.**
`score_agent.py:148-150` tells the model, in the same prompt that asks it to produce the
score: *"do not deduct for jd_coverage gaps at all"* and *"A draft that leads perfectly
with everything genuinely available should be able to reach 90+."* Classifying a gap as
`jd_coverage` removes its own scoring penalty. Downstream, `supervisor.py:52` drops
`jd_coverage` gaps from `revise()` entirely, and `report.py:111-114` presents them under
a heading that tells Austin *"Nothing in the draft can close these... no amount of
rephrasing would fix them."* There is no deterministic check on the split anywhere, and
no consequence to getting it wrong. The prose distinction at `score_agent.py:41-51` is
actually reasonably clear — this is not primarily a wording problem, it is that a
self-serving classification has zero verification.

**(b) The definition is factually wrong about what the agent can see.** The prompt says
`jd_coverage` means the candidate *"genuinely does not have [it] anywhere in the
background document"* (`score_agent.py:46-49`). But the score agent never receives
`background.md` — it receives `background_subset` (`score_agent.py:167-169`), which
`background_loader.build_subset()` (`:68-78`) filters down to
`ROLE_FAMILY_TAGS[role_family] + ALWAYS_ON_TAGS` (`config.py:55-63`). For a
`seo-growth` classification, the entire `DEV` and `PROJECTS` sections are absent. Real
experience that exists in `background.md` but wasn't loaded for this role family is
correctly-per-the-prompt classified `jd_coverage`, silently dropped from revision, and
then reported to Austin as a real career gap. That is a user-facing false statement, not
just a mislabel.

**Fix, both parts:**

1. Reword `score_agent.py:46-49` to say *"anywhere in the candidate background material
   provided below"* — stop asserting knowledge the agent doesn't have.
2. Add a deterministic backstop in `supervisor.py` alongside `_fixable_gaps`: for each
   gap tagged `jd_coverage`, tokenize its `detail`, strip stopwords, and check the tokens
   against the **full** `background.md` (`config.BACKGROUND_PATH.read_text()`, not the
   subset). Any gap whose distinctive terms appear in the full document is either
   reclassified `draft_defect` or surfaced as its own high-severity meta-issue: *"score
   agent called X a coverage gap, but background.md section [TAG] mentions it — the
   role-family subset may be wrong for this JD."* This is cheap, needs no API call, and
   catches both (a) and (b) with one mechanism.

## 3. Severity-consistency assessment

**Direct answer: yes. Mechanical checks currently outrank substance checks, by three
distinct mechanisms.** "Severity" is not one scale in this system — it is three unrelated
scales that happen to share the strings `low`/`medium`/`high`, and the acceptance
decision reads only one of them.

### Mechanism 1 — Only lint severity is wired into the acceptance decision

`main.py:112-118`:

```python
fully_accepted = (
    final_score_result.score >= config.SCORE_THRESHOLD
    and not final_score_result.integrity_flags
    and not blocking_style_issues       # <- lint severity, high|medium (main.py:110)
    and length_result.fits_one_page
    and hm_gate_result.passed           # <- a boolean; HM severity never read
)
```

- **Lint severity** (hardcoded, `structure_lint.py` / `style_lint.py`): fully gating.
  high or medium blocks acceptance.
- **HM concern severity** (LLM-assigned, `hiring_manager.py`): **never read by `main.py`
  at all.** Its only consumer is the sort at `hiring_manager.py:238`. A `[high]
  cover_letter` concern and a `[low] other` concern are identical to the acceptance
  decision — both collapse into `hm_gate_result.passed`.
- **score_agent gap severity** (LLM-assigned, `score_agent.py:37`): **read by nothing,
  anywhere.** `supervisor._fixable_gaps` (`:52`) filters on `kind`, not severity.
  `_quality_key` (`:65`) uses `len(result.gaps)`. `main.py` touches `.gaps` only at line
  178, to print them. `score_agent.py:132-138` instructs the model to emit a `"high"`
  severity gap for a missing Prospecta discipline as a NON-NEGOTIABLE check — and that
  `high` is load-bearing on nothing. (`structure_lint._check_prospecta_floor` catches the
  same thing independently at `:100-115`, which is exactly why the deterministic backstop
  is the one that works.)

**Concrete consequence:** a missing `### Education & Certifications` header
(`structure_lint.py:234`, `medium`) forces `manual_review`. A score-agent `high`-severity
gap saying the cover letter's central argument doesn't fit the company does not. The
mechanical nit outranks the substance finding, unambiguously.

### Mechanism 2 — `high` means two incompatible things inside the lint files themselves

Current `high` assignments: em dash (`style_lint.py:72`), cliche-adjacent gap-confession
phrasing (`:101`), contrast-tone framing (`structure_lint.py:268`), Prospecta floor
(`:100,109,115`), employer misattribution (`:146`), Kharon containment (`:311`).

An em dash is a cosmetic tell fixable by find-and-replace. Employer misattribution and
Kharon containment are *integrity* failures — misstating which company real work was
performed for. Both are `high`, both block equally, and both compete for the same single
stage-5 repair pass. Meanwhile a missing contact header (`:302`) is `low` and blocks
nothing, while a missing section header (`:234`) is `medium` and blocks.

**Fix:** add a fourth tier above `high` — `"critical"` — for the checks whose failure is
an integrity or fabrication problem (`structure_lint.py:146`, `:311`; `style_lint.py:101`;
and the Prospecta floor). Then make the stage-5 repair pass send critical items first and
never let `blocking_style_issues` be satisfied while a critical is outstanding. Purely
cosmetic `high` items (em dash) drop to `medium`. This costs nothing and makes the two
meanings of `high` separable.

### Mechanism 3 — `_quality_key` flattens fabrication and a word-count advisory into the same integer

`supervisor.py:65`:

```python
return (-(len(result.integrity_flags) + len(lint_issues)), -len(result.gaps), result.score)
```

An integrity flag and a `low`-severity "resume is a few words over the precheck limit"
advisory (`structure_lint.py:355`, `:370`) each contribute exactly `1`. So:

- Draft A: 1 integrity flag, 0 lint issues → first term `-1`
- Draft B: 0 integrity flags, 1 low-severity length advisory → first term `-1`

They tie, and the winner is decided by gap count and score. **The supervisor can select a
fabricating draft over a clean one that merely runs long.** The length precheck is a pure
word-count threshold and fires easily, so this is not an exotic scenario.

The same flattening burns the revision budget: `supervisor.py:99` includes `or
lint_issues` in the while condition with no severity filter, so a single `low` advisory
keeps the loop alive and consumes one of only `MAX_ITERATIONS = 3` Sonnet revise calls —
budget a real substantive gap could have used. And `supervisor.py:146` computes
`outcome_status` with `not best_lint` (any severity), directly contradicting `main.py:110`'s
deliberate decision that low-severity issues are advisory. Two files, same data,
opposite rules. (`SupervisorResult.status` happens to be unused downstream, so the
contradiction is currently latent rather than harmful — but it should be reconciled
before someone starts reading it.)

**Fix:** weight the key by severity and drop `low` from the loop condition:

```python
_SEVERITY_WEIGHT = {"critical": 100, "high": 10, "medium": 3, "low": 0}

def _quality_key(result, lint_issues):
    blockers = 25 * len(result.integrity_flags) + sum(
        _SEVERITY_WEIGHT.get(i.get("severity", "medium"), 3) for i in lint_issues
    )
    return (-blockers, -len(result.gaps), result.score)
```

and at `supervisor.py:99`, use
`[i for i in lint_issues if i.get("severity") in ("critical", "high", "medium")]`
so a `low` advisory can no longer consume an iteration.

### Summary of the pattern

The through-line across all three mechanisms, and across §1 and §2, is that **substantive
judgment enters the acceptance decision only as a single boolean** (`hm_gate_result.passed`),
while mechanical judgment enters it as a graded, itemized, self-healing list. The
mechanical path has: severity levels, a repair pass, re-verification, and a report
section. The substantive path has: one bit, computed before the last mutation. Austin's
instinct is correct — the Coursera miss was a symptom, and fixing the rubric alone does
not fix the gating.

## 4. What's already working correctly — do not "fix" these

Traced and verified, so nothing solid gets refactored away later:

1. **`hiring_gate.py` is internally consistent.** Its returned `hm_result` always
   describes its returned `draft`. On the early-advance path (`:60-61`) both come from
   the same attempt; on the cap-exhaustion path the loop reviews at `:57`, hits
   `if attempt == config.HM_MAX_ATTEMPTS: break` at `:84-85`, and returns at `:100` with
   the verdict from that same final review of that same draft. The restale in §1 is
   caused solely by `main.py` mutating the draft afterwards, not by anything in this file.

2. **Fixable HM concerns really do reach `revise()`, in correct priority order.**
   `as_gap_dicts()` sorts high → medium → low (`hiring_manager.py:215, 238`);
   `hiring_gate.py:89` passes `fixable_gaps + lint_issues` preserving that ordering; and
   `revise()` renders them in list order into the prompt (`draft_agent.py:385-387`). So
   the capped revision budget does spend its attention on whatever actually drove the
   reject. The new "3. COVER LETTER FIT AND VOICE" rubric item will route correctly *as
   long as* it isn't mis-tagged structural (§2.3) and the repaired draft gets re-reviewed
   (§1).

3. **Austin's hypothesis 3 is REFUTED — a cap-exhausted fixable concern cannot ship as
   `accepted_structurally_capped`.** `stopped_reason` is set only on the all-structural
   early-return path (`hiring_gate.py:76-81`); the cap-exhaustion return at `:100` leaves
   it at its `""` default (`:42`). `main.py:128` requires `bool(hm_gate_result.stopped_reason)`.
   So an unresolved fixable concern that runs out of attempts correctly falls through to
   `manual_review`. The label is not being misapplied by cap exhaustion. (It *can* be
   misapplied via a mis-tagged structural concern — that's §2.3, a different route.)

4. **Austin's question 4 is largely REFUTED — stage 5 runs unconditionally.**
   `main.py:65-78` executes on every path, early-advance and converged alike, so no draft
   skips the final Sonnet score or the final lint. The asymmetry that does exist is the
   *repair* pass (`:84`), and it's the inverse of the worry: the draft that needed more
   fixing gets *less* validation, not more. Covered in §1.

5. **Structural concerns are correctly excluded from `revise()`.** `hiring_gate.py:64`
   plus the reasoning at `:12-17`. Spending a Sonnet call trying to rewrite a fact about
   employment history is genuinely wasted budget. The problem is who decides what counts
   as structural (§2.3), not the exclusion itself.

6. **Lint feedback inside the hiring gate works.** `hiring_gate.py:91-98` re-lints after
   each revise/shorten and folds new issues into the next pass — v2's §2.5 recommendation,
   correctly implemented.

7. **Integrity flags are unconditionally blocking at acceptance** (`main.py:114`), with no
   severity filter and no escape hatch. Correct. The gap is that they get no *repair*
   attempt (§2.2), not that they fail to block.

8. **`_quality_key`'s gap-count tiebreaker is real and earns its place**
   (`supervisor.py:55-65`) — the docstring documents a live run where it changed the
   outcome. The severity weighting proposed in §3 should be added around it, not replace it.

9. **Sonnet for the deciding score** (`config.py:26-28`, `main.py:68-70`). The Haiku
   score-collapse finding from v2 was real and this is the right response.

## Recommended order

1. §1 — re-review the repaired draft with the HM (directly closes the Coursera class of failure)
2. §2.1 — unconditional final length check (currently shipping wrong data to the tracker)
3. §2.2 — pass integrity flags into the stage-5 repair, and let them trigger it
4. §2.3 — force document-only HM categories to fixable
5. §3 Mechanism 3 — severity-weighted `_quality_key`, drop `low` from the loop condition
6. §3 Mechanism 2 — add the `critical` tier
7. §2.4 — `jd_coverage` backstop against full `background.md`

Items 1–4 are each a handful of lines. Item 1 adds one Sonnet call on repair runs only;
the rest add no API cost.
